## Status Quo

The base prompt (`system_prompt_bills.md` + `user_prompt_bills.md`) is
zero-shot: a layout guide, a status/vote code glossary, and
clarification-priority rules — no worked examples, no reference to the
canonical member-name list. Name resolution happens in `load.py` via
`find_congresista` (`backend/database/crud/pipeline_core.py`): website
match → `CongresistaAlias` exact match → Jaro-Winkler fuzzy match at a 0.9
threshold against `Congresista.full_name` (140 rows). A failed match is
only `logger.warning`'d — not persisted, not counted anywhere queryable —
so the real failure rate had never been measured before this session.

**It has now been measured, live, against production data (see Step 0
Results below): 6.87% of every roster/roll name occurrence in the entire
loaded dataset fails to resolve to a `Congresista` record today.** Not a
rare edge case.

## Premises

1. Three prompt variants — **base** (unchanged), **few-shot** (2 worked
   input→output examples as extra turns), **full-roster** (140 canonical
   names injected into the system prompt) — built by a new local function
   in `scripts/prompt_benchmark.py`, NOT by modifying `client.py`. See
   "Request Construction" under Approach C for the exact mechanics.
2. Scored on **both** a new structural-consistency check AND the name-match
   rate (user's explicit choice, confirmed before Step 0 ran) — the
   full-roster arm's real hypothesis (reduce OCR-garbled names) is a
   different failure mode than roster/roll structure.
3. Sample pool: **one query, computed once, size-checked first.**
   `find_pending_vote_documents(kind="bill", max_pages=5, limit=90)`
   (its own `RawBillDocument.processed` flag — the extraction-attempted
   flag set in `extract.py`, distinct from `RawBillPage.processed` used in
   Step 0 above) runs a single time at script start. Before committing to
   n=30/arm, the script checks the returned count: if fewer than 90
   pending documents exist, n/arm is reduced proportionally
   (`count // 3`, floor of 10/arm — below that, abort with a clear message
   rather than run an underpowered benchmark silently). Round-robin
   assignment (`index % 3`) happens in-memory against that one result
   list. The smoke test (1 doc/arm) and the full run (remaining docs/arm)
   are the **same one-time draw** — the smoke test uses the first document
   assigned to each arm, the full run uses the rest — not independent
   resamples. This is what makes the non-determinism protection from
   Premise 3's original rationale actually hold (an earlier session
   measured a prompt-only change moving the empty-roll rate 4/10 → 7/10 on
   identical PDFs — resampling per stage would reintroduce exactly that
   confound).
4. **Zero production risk, scoped precisely:** Step 0 was pure reads
   against `find_congresista` — no writes anywhere. The three arms make
   new OpenAI extraction calls and append results to a local JSONL file
   (`scripts/prompt_benchmark_results.jsonl`) — no writes to
   `Vote`/`Attendance`/`VoteEvent`/any production table, no calls to
   `store_extraction_result` or `run_vote_load`, no changes to `client.py`.
5. A **new, benchmark-local structural check** (function, not a class,
   living in `scripts/prompt_benchmark.py`) reports sub-metrics per arm —
   see "Structural Check" under Approach C for exact predicate logic.
6. Over-prompting risk (from landscape research, "The Few-Shot Dilemma,"
   arXiv 2509.13196): the full-roster arm must be checked for
   **regression** on the structural sub-metrics, not just uplift on
   name-matching.
7. Sample size: **n=30/arm**. Risk computed via exact binomial (assuming a
   ~20% baseline pass rate for both calculations, re-verified independently
   during review): if both arms are truly equal, there's a **14.5%** chance
   the sample shows a ≥15-percentage-point swing purely by chance
   (false-positive risk); if a variant truly improves the pass rate by 20pp
   (20%→40%), there's a **9.7%** chance the sample fails to show it ahead
   by ≥5pp (false-negative risk). Report both numbers alongside any
   pass-rate comparison.
8. **Distinct cache key per arm.** `PROMPT_CACHE_KEY` ("congress-extraction
   -v3") assumes a byte-identical prefix on every call — true for base, but
   few-shot and full-roster send different `instructions` text under what
   would otherwise be the same key. Each arm uses its own key
   (`f"{PROMPT_CACHE_KEY}-base"` / `-fewshot` / `-fullroster"`) so
   cache-hit-rate and per-arm cost stay comparable and uncorrupted.

### Approach C: Measure-first, then build (CHOSEN — Step 0 complete)

**Data Flow** (added per `/plan-eng-review` — Architecture finding #3):

```
find_pending_vote_documents(kind="bill", max_pages=5, limit=90)
        │  pool size checked once: >=90 → full n=30/arm
        │  10-89 → shrink to count // 3 per arm
        │  <30 → abort with a clear message
        ▼
   [doc0, doc1, doc2, ... docN-1]        (one-time draw, never resampled)
        │  index % 3
   ┌────┴────────┬─────────────┬──────────────┐
   │    BASE     │  FEW-SHOT   │ FULL-ROSTER  │
   └────┬────────┴──────┬──────┴──────┬───────┘
        │                │              │
        ▼                ▼              ▼
   build_variant_body(model, context_text, file_id,
                       instructions=..., extra_turns=..., cache_key_suffix=...)
        │                │              │
        ▼                ▼              ▼
   client.responses.create(**body)
        │
        ├── transient error (timeout/429/5xx) → retry once, then...
        ├── non-transient error (refusal/malformed JSON) → straight to...
        │                                                        │
        ▼                                                        ▼
   score_extraction(parsed)                              error bucket (excluded
        │                                                 from pass/fail denominator)
        ├── empty / count_mismatch / party_summary_mismatch → fail
        ├── match_found & both arrays empty → no_rollcall bucket
        └── all clean → pass
        │
        ▼
   dedup extracted full_name strings → find_congresista PER UNIQUE STRING
        │  → map result back to every occurrence (Step 0's proven technique,
        │    74x fewer DB calls than per-occurrence lookup)
        ▼
   append to scripts/prompt_benchmark_results.jsonl   (incremental, one line/doc)
        │
        ▼
   after all documents: per-arm summary table — pass rate, empty/count-mismatch/
   party-summary-mismatch rates, name-match failure rate, error count, total/avg cost
```

**Request Construction** (resolves the `build_request_body` gap found in
review): `scripts/prompt_benchmark.py` defines its own
`build_variant_body(model, context_text, file_id, *, instructions=None,
extra_turns=None, cache_key_suffix="")`, importing `SYSTEM_PROMPTS["bill"]`,
`EXTRACTION_SCHEMA`, `EXPLICIT_BREAKPOINT_MODELS`, `PROMPT_CACHE_KEY`
directly from `config.py` (same constants `client.py` uses — no
duplication of data, only of the small body-assembly logic). `instructions`
defaults to `SYSTEM_PROMPTS["bill"]` (base arm); the full-roster arm passes
`SYSTEM_PROMPTS["bill"] + ROSTER_APPENDIX` (see below). `extra_turns`
defaults to `[]`; the few-shot arm passes 2 example turn-pairs prepended to
`input`, each pair shaped as `{"role": "user", "content": [...]}` (a
worked document, same content shape as the real request) followed by
`{"role": "assistant", "content": [{"type": "output_text", "text":
<that example's stored JSON as a string>}]}` — standard multi-turn
few-shot for the Responses API. `cache_key_suffix` produces the distinct
per-arm key from Premise 8.

**Full-roster appendix:** the 140 `Congresista` rows, converted from the
DB's `first_name`/`last_name` columns (no parsing needed) into the
roster's own printed convention — `SURNAME(S), GIVEN NAME(S)` — as a plain
alphabetical list appended after the system prompt's Section 3 (code
glossary), with one added instruction: *"When transcribing full_name,
match the spelling in this list exactly if the printed name is a plausible
OCR variant of one of these; if no confident match, transcribe as printed
and flag in `_uncertain_fields`."*

**Structural Check** (new function, `score_extraction(parsed) ->
dict`, benchmark-local): for each attendance/voting entry, three boolean
sub-checks — `empty` (roster/roll list has zero entries while
`overall_totals` is non-empty), `count_mismatch` (`len(roster)` /
`len(roll)` != sum of `overall_totals` fields), `party_summary_mismatch`
(sum of `party_summary[]` counts != `overall_totals`). An entry passes only
if all three are false. A record's overall pass/fail is AND across every
attendance/voting entry it contains — **except** a `match_found: true`
record whose `attendance` and `votings` arrays are BOTH empty (a bill page
with only minutes/member-letter content, no roll call in this file) is
routed to a separate `no_rollcall` bucket, not counted as a trivial pass or
as an `error` — this keeps the pass rate from being inflated by records
that have nothing to structurally check.

**Few-shot example sourcing:** 2 bill records from the 738 loaded, filtered
to those with zero `find_congresista` failures (all names resolve) AND a
clean `score_extraction` result, ordered by `step_date` descending (most
recent legislature naming conventions), first 2 taken.

**Error handling:** catch-and-continue per document, with one retry for
transient failures (added per `/plan-eng-review` — Architecture finding
#2): a timeout, 429, or 5xx gets exactly one retry with a short backoff
before being counted; a refusal, non-JSON response, or `match_found: false`
does not retry and is logged with its reason, counted in a separate
`error` bucket — excluded from the structural-check pass/fail denominator,
so "extraction didn't run cleanly" is never conflated with "extraction ran
and was structurally wrong."

**Name-match scoring (dedup required — `/plan-eng-review` Performance
finding #6):** calling `find_congresista` on every raw extracted-name
occurrence would be ~9,000 calls across all 3 arms at the ~3.4 calls/sec
measured in Step 0 (≈44 minutes just for matching, on top of API time).
Instead, per arm: collect every extracted `full_name` string, call
`find_congresista` once per **unique** string, then map results back to
occurrences for the occurrence-weighted rate — the exact technique Step 0
already used (1,022 uniques vs 75,905 occurrences, a 74x reduction).

**Sample validity check (added per `/plan-eng-review` outside voice):**
the 30/arm sample is drawn from `find_pending_vote_documents` (the
unprocessed backlog) — a different population than the 738 already
-processed records Step 0 measured. Nothing guarantees the two populations
share a failure rate. The summary (below) compares the **base arm's own**
name-match failure rate against the 6.87% Step 0 baseline: if it diverges
by more than ~5 percentage points, the report flags the sample as
**possibly non-representative** rather than presenting the other arms'
deltas as straightforwardly meaningful.

**Reporting:** after all 90 documents (30/arm) complete, the same script
prints a per-arm summary table — pass rate, empty rate, count-mismatch
rate, party-summary-mismatch rate, name-match failure rate (via the deduped
`find_congresista` lookup above), error count, total/avg cost, plus the
sample-validity flag above — no separate reporting script needed.

**Model/cost:** `gpt-5.6-luna` (repo default), synchronous
`client.responses.create` (matching every prior sample this session, not
the Batch API). 90 documents total (30/arm × 3 arms) — the smoke-test call
for each arm is the first of its 30, not an additional call, so 90 is the
full call count, not 270. Using `config.py`'s own conservative
`DEFAULT_COST_ESTIMATE_PER_DOC` ($0.01) as a ceiling: **~$0.90 estimated
maximum** — real cost is likely materially lower given `gpt-5.6-luna`'s
actual per-token pricing, but no harder estimate is claimed here.

  Effort: M — Step 0 already done; remaining is `build_variant_body`,
  the structural check, the roster appendix, and the scoring loop
  Risk: Low — read-only pre-check already de-risked the go/no-go call;
  remaining risk is standard API-call/cost risk (~$3 ceiling), not
  architectural risk

| Codepath | Realistic failure | Test? | Error handling? | Silent? |
